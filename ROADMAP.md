# ZeroTacky roadmap to "final state" (drafted 10/16 evening, Slate; Kurt to edit)

Two tracks run at once. `main` stays the meet-day build for 10/24 and only takes the five sprint items plus bug fixes. A `v2` branch takes everything that needs accounts. They merge after the meet.

## 1. Branches and environments

| | `main` (demo / meet-day) | `v2` (final state) |
|---|---|---|
| Deploys to | https://zerotacky-lime.vercel.app (Vercel production) | Vercel preview URL per push (`zerotacky-git-v2-*.vercel.app`), or a second Vercel project `zerotacky-v2` if we want a stable URL |
| Supabase | `kagitbfthapxmaljsdtz` (the real meet's data) | a second project, `zerotacky-staging`; v2 testing never touches meet-day rows |
| Takes | sprint items 1-5, bug fixes, UI polish that both branches want | auth, profiles, promoter dashboard, registration, Supabase-backed shows/gyms |
| Freeze | 10/22 evening through the meet; hotfixes only | none |
| After 10/24 | collect meet-day issues, fix on `main` | merge `main` into `v2` (fixes flow forward), finish, then `v2` becomes `main`; the old demo meet stays as `isDemo` fixtures |

Rule: both branches get the same UI fix on the same day (I cherry-pick), so the demo never drifts behind on things a user would notice.

## 5. Back burner (Kurt's ideas, parked 10/17, not scheduled)
- **Strongman-friendly gym directory.** (`/gyms` already exists with labelled demo fixtures from Argon's skeleton; this is the real-data version.) Chains vary by location (one Planet Fitness is a hotel gym, another has power racks; one Crunch has turf, sleds and sandbags, another only kettlebells), so the useful unit is the individual gym, not the brand. Shape if we build it: a `gyms` table (name, address, geo), a fixed equipment checklist (yoke, log, axle, stones, sandbags, sled/turf, farmer's handles, power rack, platform, car deadlift frame, Husafell, keg), and per-user "I trained here, it has X" confirmations with dates so stale entries age out. Anyone signed in can add a gym; equipment claims show the count and recency of confirmations rather than a single owner's word. Moderation is the real cost (duplicates, closed gyms, spam), so this waits until there are enough accounts to confirm each other.

The honest constraint: Instagram's Basic Display API was retired in December 2024 and the Graph API only serves Business/Creator accounts that OAuth in; a plain "show my latest posts" for personal accounts does not exist any more. Realistic options: (a) a promoter pastes Instagram post URLs on a show page and we render them with Instagram's oEmbed (needs a Meta app and the oEmbed permission; renders their embed, no copy stored), (b) athletes put their handle on the profile and we link out, no thumbnails, (c) hosted uploads through Supabase Storage with a size cap and a report button, which is the thing Kurt would rather not run. ## 6. Gyms (Kurt 10/20: build right after the meet; gym owners can be recruited early to drum up conversation)
Order of work, each shippable alone:
1. **`gyms` table + owner form** (`014_gyms.sql`): id, slug, name, owner_id, city, state, street_address, zip, lat, lng, website_url, contact, day_pass_availability, day_pass_price, day_pass_url, drop_in_policy, drop_in_hours, equipment text[] (ids from `GYM_EQUIPMENT`), equipment_notes jsonb (per-item details, free text), socials jsonb (same shape as profiles), theme jsonb, is_listed boolean, created_at/updated_at. RLS: public read where is_listed, owner insert/update/delete. "My Gym" page under Account for `is_gym_owner`: one gym per owner to start (a second needs a second account or a later `gym_members` table). Listing goes live on save; moderation later (back-burner note in section 5 still applies for the crowd-sourced version).
2. **Public `/gyms` from the database**: real gyms first, the three fixtures stay as labelled demos until there are 5 real listings, then drop them. `/gyms/<slug>` reads the table; home_gym_name on profiles becomes a link when it matches a listed gym (store `home_gym_id` alongside the free text).
3. **Zip + radius filter** (Kurt 10/20, "more useful than state"): zip input + "within 25 / 50 / 100 miles" select, haversine in `lib/geo.ts` against the gym's lat/lng, results sorted by distance with the miles shown. Zip centroids from the Census ZCTA gazetteer (public domain, ~33k rows) behind a tiny API route so the client never downloads the table; gym lat/lng filled at save from the address via the Census geocoder (free, no key), zip centroid as the fallback. State select stays as a secondary filter. Fixtures get lat/lng so the filter works on demos.
4. **Gym <-> shows both ways**: `meets.host_gym_id` (nullable) set from the promoter's meet settings (pick from listed gyms, or free text as today); show page "Hosted at" links to the gym; gym page lists upcoming and past shows from `meets` (replaces fixture `hostedShowSlugs`).
5. **Colour ways**: `theme` jsonb on gyms and on meets (primary, secondary, background, text, logo path), set by the owner/promoter from a small picker (presets + custom hex), applied to the public gym page, the show page, and the live board for everyone who opens them. Honour contrast: refuse a pair below 4.5:1. Scorer phones keep their own theme.
6. **Gym extras to add to the form once owners ask** (from the 10/20 audit): strongman class / open-training schedule, coaching available (ties to profile is_trainer), gym Instagram, parking and loading-dock notes, "visiting athletes welcome" flag, photo of the implements.
Training directory (profiles.is_trainer) follows gyms: `/trainers` filtered by location and in-person/online, pulling from profiles with an opt-in `list_me` flag so nobody is listed by accident.
