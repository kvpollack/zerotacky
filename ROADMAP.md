# ZeroTacky roadmap to "final state" (drafted 10/16 evening, Slate; Kurt to edit)

Two tracks run at once. `main` stays the meet-day build for 10/24 and only takes the five sprint items plus bug fixes. A `v2` branch takes everything that needs accounts. They merge after the meet.

## 1. Branches and environments

| | `main` (demo / meet-day) | `v2` (final state) |
|---|---|---|
| Deploys to | https://zerotacky-lime.vercel.app (Vercel production) | Vercel preview URL per push (`zerotacky-git-v2-*.vercel.app`), or a second Vercel project `zerotacky-v2` if we want a stable URL |
| Supabase | `kagitbfthapxmaljsdtz` (the real meet's data) | a second project, `zerotacky-staging`; v2 testing never touches meet-day rows |
| Takes | sprint items 1-5, bug fixes, UI polish that both branches want | auth, profiles, promoter dashboard, registration, Supabase-backed shows/gyms |
| Freeze | 10/22 evening through the meet; hotfixes only | none |
| After 10/24 | collect meet-day issues, fix on `main` | merge `main` into `v2` (fixes flow forward), finish, then `v2` becomes `main`; the old demo meet stays as `isDemo` fixtures |

Rule: both branches get the same UI fix on the same day (I cherry-pick), so the demo never drifts behind on things a user would notice.

## 2. Milestones

- **M0 (10/17 to 10/22, `main`)**: Station naming; Meet Setup reorder (details, divisions, events, athletes, theme last); Config/Advanced bar hiding everything but Results CSV; live overall leaderboard; landscape/phone toggle for leaderboard and Pit Crew; theme ideation plus configure button and day/night toggle on the website landing. One-command meet export plus restore (`scripts/dump_meet.py`, done 10/17; see PHASE1_SYNC_NOTES.md "Backup") as the backup for 10/24, since the free Supabase tier has no point-in-time recovery.
- **M1 (10/24)**: All Out Strongfest. Judges and pit crew on phones, leaderboard on a TV. Capture every issue in `PHASE1_SYNC_NOTES.md`.
- **M2 (start 10/17 in parallel, `v2`)**: accounts. Supabase Auth (email magic link + password; Google optional), `profiles` table (display name, role flags: athlete / promoter / gym owner, all three can be true), Account page replaces the persona switcher in `AccountPreviewClient`. Publish moves from the shared publish key to the signed-in promoter: `zt_publish_meet` gets an authenticated path, `meets.owner_id` and `meet_members` (already in `001_schema.sql`) become the authority. Migration `003_auth.sql` (002 is station labels).
- **M3 (`v2`, built 10/17, staging-verified)**: promoter dashboard in the browser, backed by Supabase. Create and edit meets with the existing Meet Builder; listing columns on `meets` (`competition_status`, `registration_status`, `results_status`, `is_public_listed`, `venue`, `federation`, `entry_fee_display`, `registration_deadline`, `athlete_cap`, `promoter_contact`); `/shows` and `/shows/[slug]` read Supabase through `lib/website/data.ts` (ISR, 60 s); athlete registration moved up from M4: `/register/<slug>` writes `registrations` through `zt_submit_registration`, the promoter accepts or declines through `zt_set_registration_status`, accepted rows become roster athletes (and so reach the judge phones). Waiver acceptance stamp plus the waiver text version (`waiver_version`). Migrations, in order: `004_result_guard.sql` (trigger: no delete of a scored athlete/event/division; also goes to prod), `005_listing.sql` (listing columns, registrations, the RPCs), `006_ownership.sql` (column-level grants on `meets`/`profiles`, owner-only `meet_members` changes, `zt_transfer_ownership`, `zt_publish_meet` claim fix), `007_gate_fixes.sql` (Astra gate audit 10/17 pm: registration FK column-list SET NULL, approved waiver versions, unique active registration, throttles, `zt_update_listing`, join RPC without `admin_pin` + `zt_check_admin_pin`; **v2 only until the merge, see the file header**), `008_publish_guards.sql` (Astra rehearsal 10/17 evening, revised gate 2 night: `zt_publish_meet` refuses to drop an accepted registrant and keeps the PIN when the phone sends none; no direct UPDATE on `meets`; TRUNCATE/REFERENCES/TRIGGER revoked everywhere; v2 only with 007). Gate 2 (10/17 night) also changed policy in 007: the cap is an intake limit (submissions and acceptance), an over-cap floor roster still saves; the registration keeps the submitted division and the roster row is the effective one. Phone keeps meet-day edits only. Still fixture-only until a later milestone: `/promoter/[serverId]` and `/register/<slug>` resolve in the browser, so unknown ids render an in-page not-found with HTTP 200 (Astra M13).
- **M4 (`v2`)**: registration polish. Athlete-side account linkage (a signed-in athlete sees their own entries), waitlist promotion when a spot opens, payments deferred: `registrations.paid` exists and `meets.entry_fee_display` is text for the listing; a `registration_fee` amount column and Stripe come when a promoter actually charges. Server-rendered lookups with real 404s for `/promoter/[serverId]` and `/register/<slug>` (M13).
- **M5 (`v2`)**: gyms directory with owner claims and edits; results archive (finalized meets publish standings with tie placement `1, 1, 3`).
- **M6**: `v2` becomes `main`. Custom domain, Vercel Pro if we charge anyone, demo banner off, `/website` promoted to `/` with the splash's two buttons folded into the landing page.

## 4. Who does what: Fable 5.1 (Slate), Gemini 4 Argon, GPT-6 Astra

The benchmark gaps between the three are a few points and vendor-reported. What actually separates them for this project is access: Slate has the repo, tests, Supabase, GitHub push, the browser panel and months of memory; Argon in Kurt's Gemini app has none of that and cannot run anything; Astra in an Aki thread has the same tools as Slate but no history. So:

- **Slate (Fable 5.1): integrator and owner of both branches.** All code lands through Slate: run tests, apply migrations, push, keep notes and memory. Fable 5.1 has the top coding-agent score inside a harness (Artificial Analysis coding-agent index 70 vs Astra 67) and the cheapest cache reads for long sessions, which is the shape of this work.
- **Argon (Kurt's personal Gemini): big self-contained drafts.** Argon leads long-horizon software engineering (DeepSWE 77.9 vs 74.1 Astra, 67.4 Fable) and is the only model with 1M output tokens per response, so whole-feature skeletons and long documents are where it pays off: promoter dashboard UI, registration flow screens, migration drafts with RLS, theme system, privacy policy and terms. Two rules from today's handoff: give it the exact contracts (`lib/types.ts`, `001_schema.sql`, the component it must plug into) and require tests; treat its output as untested until Slate runs it (the filters bug and the fake 404s were both in code Argon never executed).
- **Astra (GPT-6 Astra, thread here): audit and adversarial testing.** Astra leads frontier engineering (FrontierSWE 65.5) and computer use (OSWorld 72.6), and ties Argon on vulnerability remediation. Use it for three things: security review of every migration's RLS before it reaches prod; browser-driven end-to-end runs against the preview URL (two phones joining, publish, config refresh, sign-up flow); and the hardest debugging when Slate is stuck. It costs 5x the cheaper OpenAI model per token, so point it at review and hard problems, not bulk code.

Worst case collapses to the same shape: Slate builds, Argon drafts large pieces, Astra audits. Cadence per feature: Slate writes the brief and contracts, Argon drafts, Slate integrates and tests, Astra reviews on the preview URL, Slate fixes and merges.

## 5. Back burner (Kurt's ideas, parked 10/17, not scheduled)
- **Strongman-friendly gym directory.** (`/gyms` already exists with labelled demo fixtures from Argon's skeleton; this is the real-data version.) Chains vary by location (one Planet Fitness is a hotel gym, another has power racks; one Crunch has turf, sleds and sandbags, another only kettlebells), so the useful unit is the individual gym, not the brand. Shape if we build it: a `gyms` table (name, address, geo), a fixed equipment checklist (yoke, log, axle, stones, sandbags, sled/turf, farmer's handles, power rack, platform, car deadlift frame, Husafell, keg), and per-user "I trained here, it has X" confirmations with dates so stale entries age out. Anyone signed in can add a gym; equipment claims show the count and recency of confirmations rather than a single owner's word. Moderation is the real cost (duplicates, closed gyms, spam), so this waits until there are enough accounts to confirm each other.
- **Photos on shows and profiles.** Preferred: link Instagram rather than host uploads (no storage, no moderation of nudity/abuse, no takedown work). The honest constraint: Instagram's Basic Display API was retired in December 2024 and the Graph API only serves Business/Creator accounts that OAuth in; a plain "show my latest posts" for personal accounts does not exist any more. Realistic options: (a) a promoter pastes Instagram post URLs on a show page and we render them with Instagram's oEmbed (needs a Meta app and the oEmbed permission; renders their embed, no copy stored), (b) athletes put their handle on the profile and we link out, no thumbnails, (c) hosted uploads through Supabase Storage with a size cap and a report button, which is the thing Kurt would rather not run. Start with (b) plus (a) for promoters; revisit uploads only if promoters ask for a gallery.
- **Branded transactional email (parked 10/19).** Auth templates are in `emails/`. Registration mail (request received, accepted, declined, waitlisted, meet-day reminder) needs a send path the app does not have: a Postgres trigger on `registrations` -> Supabase database webhook or edge function -> Resend API, with the promoter's name and contact in the body. Same layout as the auth templates. Do after the 10/24 meet.
- **Trainer directory / marketplace (Kurt, 10/19).** Online coaching is expensive and uneven; let people sign up as trainers, upload certifications, and publish a "hire me" page. Reviews from clients, a composite score out of 5 on fixed dimensions (programming quality, accessibility and responsiveness, value for money, resources provided), and LinkedIn-style endorsements for specific skills (peaking for competition, working with women with PCOS, training around injuries, log press). Slate's notes, for when this is scheduled:
  - This is a second product with its own trust problem. The scoring only means something if reviews come from verified clients (paid through the platform, or the trainer confirms the engagement and the client confirms it back); open reviews get gamed within a month. Endorsements are cheaper to launch because they carry less weight and can be limited to people who have shared a meet roster or an account history with the trainer.
  - Certification upload is document storage plus a verification claim. Several issuers have public lookups (NSCA, NASM, ISSA, USAW); verify against those where possible and display "verified with issuer" vs "uploaded, not verified". Store the document private, show the badge.
  - Liability shifts: coaching advice and injuries sit outside the meet waiver. Terms would need a marketplace section (ZeroTacky is a directory, not the trainer), and counsel should see it before launch.
  - Payments are optional at first (directory + contact form), but "verified client" reviews are far easier with Stripe Connect in the loop, so the review model and the payments model should be designed together.
  - Fits the existing pieces: accounts, athlete profiles, meet history (a trainer's athletes' results are a credential nobody else can show). That is the angle no generic coaching marketplace has.
  - **First step (Kurt 10/19, cheap):** a "I coach / train athletes" opt-in on the profile with the note "We are building a training network; checking this puts you on the list." No directory yet; it is the interest signal and the seed list for the marketplace.
- **Org membership cards on profiles (Kurt 10/19).** Athletes upload a photo or screenshot of their federation membership card (Strongman Corp, USS, etc.) with the expiration date typed in; the promoter's registration view shows "membership: USS, expires 2027-03-01, card uploaded" so nobody checks paper on meet day. No issuer has a lookup API we can trust, so the image is the evidence and the date is self-declared. Automated reminder email to registered athletes who have not uploaded one (needs the registration email send path above). Private storage bucket, promoter-only read, delete on request (privacy page gains a row).
- **Gym-supplied waivers (Kurt 10/19).** A gym or promoter uploads their own waiver PDF/text; athletes accept it at registration alongside ours, so nothing is signed on paper at the door. Legal check before building: we would be the record-keeper of acceptance for a document we did not write. Counsel question to add to the packet: does hosting and timestamping a third party's waiver expose ZeroTacky beyond the processor role described in the privacy policy? Kurt's read is no; confirm before shipping.
- **Stations separate from Divisions (Kurt 10/19, UI).** Divisions get nailed down first; stations are decided later from sign-ups and floor space. Move station setup out of the Divisions step into its own tab or an "assign divisions to stations" screen that appears once divisions exist. Also: the run order methodology toggle needs a plain explanation of each option on the screen itself, not a label alone.
