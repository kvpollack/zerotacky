## What to audit (in priority order)

1. **Migration 024: publish key retired** (`supabase/024_drop_publish_key.sql`). New `zt_publish_meet(p_meet, p_divisions, p_events, p_athletes, p_results)` requires `auth.uid()`; an existing meet needs the caller in `meet_members`; an ownerless meet (owner account deleted, `meets.owner_id` is "on delete set null") can be taken over only by a remaining member, anyone else is refused. A shim overload `zt_publish_meet(p_key, ...)` ignores the key and calls the new function so phones still on the previous build keep publishing; it goes in a later migration. Both overloads: revoked from public and anon, granted to authenticated and service_role. `publish_keys` dropped (1 row on each DB, 0 ownerless meets, every owner had a member row before the change). Verified by me: anon bearer gets 401 on both overloads (staging and the fake), a signed-in staging test meet published through both and was deleted. Questions: is there any remaining write path that does not need an account (RLS on `meets`, `divisions`, `events`, `athletes`; the 011 grant path for `results`/`live_state` is by design)? Can a signed-in non-member publish to an existing slug and get anything written before the member check (`v_id` resolution by slug happens first)? Is the ownerless refusal message right, or should it point at `zt_transfer_ownership`? Does PostgREST ever pick the wrong overload when a client sends `p_key: null`?

2. **App side of 024.** `lib/sync/meetApi.ts publishMeet(client, state, extra)` sends no `p_key`; `lib/sync/controller.ts publish(extra)` refuses without a token before any network call, tags the link `auth: 'account'` with `userId`; links written as `'key'` by older builds are still read and stay accountless (sign-out does not pause them); `hooks/useMeetSync.js` drops the saved key from localStorage on mount; `components/setup/SyncPanel.jsx` lost the "old publish key saved" notice. Questions: a phone with a legacy `'key'` admin link, now signed in, re-publishes: does the link become `'account'` cleanly and does the next sign-out pause it as expected? A phone with a legacy key link and no account: can it still flush scores through its grant, and what does the Sync panel tell it? Anything in the scorer still reading `ZEROTACKY_PUBLISH_KEY_V1`?

3. **MS-12: one theme source** (`components/website/WebsiteThemeFrame.tsx` now takes `className`, `override`, `onUserChange`; `components/shell/RootLanding.tsx`, `app/join/JoinClient.tsx`, `app/m/[slug]/ScoreboardClient.tsx` wrap in it with `WebsiteThemeControls`). Shared pref `ZEROTACKY_THEME_V1` applies on `/`, `/join`, `/m/<slug>`; the board's `?theme=` wins until the user touches the controls, at which point the override is dropped and the pref changes. Board header wraps its right cluster (theme, TV toggle, updated stamp) under the title at 375. Questions: hydration warnings on first paint of `/` and `/join` (frame renders Steel until mount)? TV layout (`?layout=tv`) with the controls present: does the palette popover position sensibly at 1920 wide, and does the Day/Night button after a `?theme=` override flip to the right side? The scorer (`components/strongman-app.jsx`) still owns its own `useTheme()` call; does a pick in the scorer show on `/join` on the same phone and vice versa?

4. **MS-13: skip link and phone header** (`components/website/WebsiteShell.tsx`, `WebsiteAccountChip compact`). `a[href="#zt-main"]` sr-only until focus, `main#zt-main tabIndex=-1`. Below sm: wordmark row with icon-only account chip (aria-label "Account: <name>"), "Join", theme controls; nav as one horizontally scrolling row (scrollbar hidden). sm and up unchanged. Measured 117 px at 375 (was ~210). Questions: is the active nav item discoverable when it sits off-screen in the scroll row (Account is 6th)? Does the hidden scrollbar leave any affordance that the row scrolls? Skip link order in the tab sequence; focus ring visible on the link in Daylight; does `main:focus` outline removal hurt anything? Signed-out phones: the chip renders nothing, so the row is wordmark + Join + theme; confirm nothing jumps when the chip mounts after auth loads.

5. **MS-14: show page stamp and directions** (`lib/website/format.ts`, `components/website/ShowDetailClient.tsx`). `UpdatedStamp` renders the ISO instant as the reader's local time after mount, date-only before (hydration-safe); `<time dateTime>` carries the ISO. Venue block: facility and address on separate lines; "Directions" opens a Google Maps search built from facility, street, city, state, zip, only when a street or city+state exists. Em-dashes removed from the provisional label and landing copy; page titles keep theirs on purpose. Questions: a show with `lastUpdatedIso` but a Supabase `updated_at` with microseconds, does `new Date()` parse it everywhere Safari included? Does the live snapshot stamp still make sense when it is a server `latestServerAt` rather than a meet update? Any show fixture whose venue lacks a street but has a misleading facility name that would make the Maps search wrong?
