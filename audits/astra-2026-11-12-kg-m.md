# Astra kg / m build audit

**Verdict: HOLD before relying on unit changes across live devices.**

Audited `main 86514d46257948b0a2746a82f296f66b8cdda73b`, November 12, 2026. **10 findings: 3 High, 6 Medium, 1 Low.** This is an audit handoff. No application fixes, pushes, remote mutations, or messages were made.

The selected design is sound. Store weights and distances in the meet's chosen units, retain the historical field names, and keep conversion out of scoring and loading arithmetic. The blocking gaps are in how devices retain and replace meet configuration. A correct unit label helper cannot correct a device holding the wrong `meet.units`.

## Findings

### KM-01 | High | Metric-to-imperial refresh does not clear the judge phone's metric flag

**Source:** `lib/sync/mapping.ts:99-110`; `hooks/useMeetSync.js:73-84`.

`rowToMeet` deliberately omits `units` for imperial. The hook applies a refreshed meet by spreading it over the old meet. An absent property cannot clear the old `units: 'metric'`. Plates, events, and divisions refresh, but the judge/pit-crew device continues labeling the new imperial numbers as kg/m.

**Reproduced:** Start a metric device with no scores, change the synthetic server to imperial, then run the real controller's config pull with the hook's merge logic. Server is imperial, the returned config has no units key, and the device remains metric. See `sync.json.metricToImperial` and `pure.json.mergeBackToImperial`.

**Fix:** Explicitly replace normalized units on every config merge, or replace the public meet object while preserving only deliberate local fields such as ID/PIN. Add both-direction tests through the hook merge as well as mapping round trips.

**Acceptance:** Metric to imperial must update labels and plate inventory together on a connected judge device, without reload.

### KM-02 | High | Admin phones ignore dashboard unit changes and can republish stale units

**Source:** `lib/sync/controller.ts:275-276,494-503`; `hooks/useMeetSync.js:165-179`; `supabase/059_meet_units.sql:69-72,98`.

The controller fetches changed configuration only for links with `role === 'device'`. An admin phone records the new config timestamp without loading the new units, events, or plates. Before scores exist, its next config edit can auto-publish the stale unit choice over the dashboard's newer choice. Once scores exist, the explicit flip is refused, but the admin can still display and enter numbers under its stale unit choice.

**Reproduced:** The controller simulation advances the admin's config timestamp while leaving its old metric state and producing zero config patches. The exact SQL bodies permit a unit change while the results table is empty. See `sync.json.adminConfig` and `sql.json`.

**Fix:** Give units/config an authoritative revision across dashboard and admin devices. Refresh before edits and publication; reject stale config publication rather than treating the admin phone as permanently authoritative. Do not silently discard unsaved edits when adding refresh behavior.

**Acceptance:** Open admin phone, change units in the dashboard, then edit a harmless phone field. The newer units must survive, and the phone must either refresh or require conflict resolution.

### KM-03 | High | Offline scores have no unit/config provenance and upload before refresh

**Source:** `lib/sync/controller.ts:429-436,442-455,538-541`; `lib/sync/mapping.ts:90-95`; `supabase/001_schema.sql:111-119`; `supabase/059_meet_units.sql:69-72,232-234`.

The lock checks results already on the server. A disconnected judge can have the first score queued while the server still permits a unit flip. Reconnection calls `flush()` before `pull()`. The result row carries the numeric payload but no unit or config revision. The server cannot distinguish 220 lb from 220 kg, and the later refresh makes the phone display the stored 220 in the new unit.

**Reproduced:** Queue `maxWeightLbs: 220` on an imperial max-weight device. Change the empty synthetic server meet to metric, then tick. The first request is a results POST, it stores 220, and the device subsequently becomes metric with idle sync status. The SQL harness separately shows a legal flip followed by an untagged result insert. `results_stamp` only checks timestamps; it does not check unit provenance. See `sync.json.offlineResult` and `sql.json`.

A same-ID snapshot/file restore can also replace local units while the sync link remains. The SQL config flip guard does not validate the meaning of result rows uploaded through the separate queue.

**Fix:** Record the unit/config revision under which each result was entered and reject or quarantine mismatches on the server. Refresh before flushing, but do not merely relabel already queued results after the refresh. Require explicit resolution for old-unit scores. Serialize unit changes and first-result admission on the same meet/revision boundary.

**Acceptance:** Queue a score offline, legally flip the empty server meet, then reconnect. The old-unit score must be held with an actionable explanation, never silently accepted as the new unit.

### KM-04 | Medium | An already-open public board/TV never refreshes units

**Source:** `app/m/[slug]/ScoreboardClient.tsx:109-132,143-157`; `components/tv/TvBoard.tsx:50,103`.

Initial loading includes units. Later polls merge results and athletes and update lifecycle status, but ignore `chg.meetUpdatedAt` and never fetch changed configuration. Both the phone board and TV use that retained state. A board opened before a legal pre-score flip can show new scores with old unit labels until reload.

**Evidence level:** Direct source trace. A live deployed flip was not performed. `pullChanges` exposes the config timestamp, but this consumer does not use it. The defect is in retained in-memory state. The SELECT includes units; CDN behavior was not tested.

**Fix:** Re-fetch and replace configuration when its revision changes, including explicit normalized units. Apply scores and their matching config coherently.

### KM-05 | Medium | Picker toggle reinterprets accepted free text without converting it

**Source:** `lib/website/groupPicker.ts:205-224`; `components/website/GroupPickerClient.tsx:48-64`.

The parser accepts a first number from text such as `225 x 3`, but `convertDisplayUnit` only converts bare numeric strings. Switching from lb to kg leaves `225 x 3` unchanged, and the parser then treats it as 225 kg.

**Reproduced in Chrome:** On the synthetic metric show, entering that text under lb gives a Group 1 recommendation. Toggling kg leaves the text unchanged and recommends Group 2. Canonical input changes from 225 lb to 496 lb. See `ui.json`, `picker-expression.png`, and `pure.json.pickerToggle`.

**Fix:** Use one input grammar for parsing and conversion. Prefer a canonical numeric value separate from display text. Reject unsupported expressions rather than accepting them in one path and skipping conversion in another. Explicitly labeled text such as `140 kg` should keep its meaning.

### KM-06 | Medium | Picker round trips and PR seeding change canonical strength

**Source:** `lib/website/groupPicker.ts:206-230`; `components/website/GroupPickerClient.tsx:37-64`.

Canonical pounds are recomputed from rounded display text. Conversion rounds to whole kilograms and back to whole pounds; `parseLiftInput` also rounds pounds. The result is not invariant under a display-only toggle.

**Reproduced:** `225.5 lb -> 102 kg -> 225 lb` in Chrome. A 54 lb input becomes 24 kg, then parses as 53 lb. At a 48.6 lb event target, the verdict changes from Within reach to Above band. See `ui.json` and `pure.json.boundary`. PR seeding uses the same whole-unit display round trip.

**Fix:** Store full-precision canonical pounds independently. Round only rendered text, and change canonical values only when the athlete edits an input. A display toggle or arriving PR seed must not alter recommendation inputs.

### KM-07 | Medium | SQL accepts metric courses the UI later hides

**Source:** `supabase/041_event_spec_guard_types.sql:28-29,51-57`; `lib/events/spec.ts:84-94,123-125,166-174`; `lib/meetBuilder.ts:897-958`.

1610 itself fits below 5280, but the shared backstop permits 1610.5 through 5280 on a metric meet. The form rejects those values, `validateMeet` does not catch them, and metric display normalization removes the course. Imports/API saves can therefore succeed while the published course disappears.

**Reproduced:** Exact SQL save accepts 2000 on a metric meet. `validateMeet` returns OK, `validateEventSpec` rejects it, and `specSegments` returns an empty list. SQL errors still say feet and half-foot steps. See `sql.json` and `pure.json.spec`.

**Fix:** Apply the selected unit's course limit at the SQL event-write boundary and in whole-state validation/import. Keep an old signature only as a compatibility wrapper if necessary. Validate retained courses during a unit flip as well.

### KM-08 | Medium | Non-UI creation/adoption defaults still supply imperial plates to metric meets

**Source:** `lib/meetBuilder.ts:123-142`; `supabase/059_meet_units.sql:87-89,290`; `supabase/060_adopt_units.sql:51-61`; `supabase/001_schema.sql` meet default.

The radio button supplies metric defaults, but `normalizeState` falls back to `ALL_POSSIBLE_PLATES` without considering units. SQL publish also defaults to the imperial array. Adoption omits inventory entirely and takes that same column default.

**Reproduced:** A metric state without inventory gets `[100,55,45,35,25,15,10,5,2.5]`. An exact SQL metric publish without plates does too. Read-only staging confirms the adopted Scarlet metric meet has this imperial default inventory. Completed imported results are unaffected today, but its setup/any reuse has an inconsistent default. See `pure.json.missingPlates`, `sql.json`, and `staging-fixtures.json`.

**Fix:** Choose defaults by normalized units in every constructor and ingestion path. Preserve an explicitly supplied custom inventory, even if its denominations happen to resemble the other system.

### KM-09 | Medium | Federation bodyweight column is unlabeled pounds beside kg event results

**Source:** `lib/exportFederation.ts:42,59-66`; `lib/roster/import.ts:114-124`.

Event cells are correctly labeled, but `Bodyweight` is a bare number. Bodyweight remains canonical pounds independently of the meet's scoring units. A metric CSV can therefore contain `220.5` under Bodyweight beside `100 kg` and `20 m`, with no declaration that the bodyweight is pounds.

**Reproduced:** See `federation.csv`. A human or importer assuming metric throughout could read a roughly 100 kg athlete as 220.5 kg. No specific federation importer was tested, and this pack does not claim a federation-defined machine schema.

**Fix:** Name the column `Bodyweight (lb)` or add explicit bodyweight-unit metadata. For machine interchange, define a versioned schema with separate numeric value/unit fields rather than parsing the human results sheet. Do not infer bodyweight units from `meet.units`.

### KM-10 | Low | PR comparison rounds before ranking

**Source:** `lib/units.ts:75-80`; `lib/website/prBoard.ts:56-79,135-136`.

`toLb` and `toFt` round metric values to one decimal before comparison; imperial values keep their original precision. This can turn a real difference into a tie and retain the earlier history entry as the best.

**Reproduced:** 10 m is 32.80839895 ft, but ranks equal to 32.8 ft and loses when that row is first. A 100.025 kg max is 220.5173777 lb but similarly loses to a first-listed 220.5 lb row. See `pure.json.prDistancePrecision` and `prPrecision`. The practical effect is confined to close values.

**Fix:** Use unrounded conversion for ranking and ratios. Keep display rounding separate; if an equality tolerance is desired, define it consistently for both systems.

## Design decisions, separate from defects

### D1. Require review or re-entry of setup numbers on a flip

**Include collars, tares, light-tier weights, and course distances.** Also include main division weights and rising-bar arrays. Do not convert them automatically under option B.

The present implementation deliberately changes only `units` and `availablePlates`. Chrome confirmed `100 lbs (light 60) / 50 ft course` immediately becomes `100 kg (light 60) / 50 m course`; tare remains 45 and both collar values remain 5. This matches the note that switching converts nothing, so it is a design risk rather than an undisclosed conversion bug.

My preferred behavior is an explicit flip confirmation that clears unit-bearing numeric setup, marks it incomplete, and requires re-entry before scoring/publishing. If retaining values is intentional, require a visible review checklist and block use until confirmed. Include user-authored weight callouts and fixed-implement descriptions in review; they may still say lb. Leave bodyweight, `weightCapKg`, reps, time, implement counts, and nonnumeric pin/height labels alone.

### D2. Show PR mirrors on imperial rows too

**Add mirrors to imperial PR rows.** Mixed history is easier to compare when every weight best has both units. The current metric-only mirror is explicitly implemented and tested. Current output is `200 kg (441 lb)` versus `440 lb`. Distances have no mirror in either direction; adding both-direction distance mirrors would make kg/m history equally usable.

## Fix order and disposition

1. **First resolve KM-01 through KM-03 together.** Establish explicit units/config provenance, authoritative refresh, and rejection of mismatched queued scores. A client-only label patch does not close the data-integrity gap.
2. Fix KM-04, implement the D1 flip workflow, and close KM-07/KM-08 so new or imported setup is consistent.
3. Fix picker input handling and precision (KM-05/KM-06), export metadata (KM-09), and PR precision (KM-10). Add D2 mirrors in the same PR display pass.
4. Recheck with two connected devices and one offline queue, both flip directions, same-ID restore, metric import/adoption, both exports, and a real claimed metric profile.

All ten findings remain **open, handed to the build owner**. D1 and D2 are recommendations for explicit product disposition. No finding was silently fixed during this independent audit. A concurrent first-result/unit-change race was not exercised; include it in the server admission/revision tests because the current lock is an existence check rather than a result-provenance check.
