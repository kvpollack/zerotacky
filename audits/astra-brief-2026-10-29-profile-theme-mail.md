## What to audit (in priority order)

1. **Registration emails (031)** (`supabase/031_registration_email.sql`, `app/api/registration-email/route.ts`, `lib/email/*`). POST `{registrationId, kind: 'received' | 'decision', force?}` with the user's Bearer token. The route never trusts an address from the client: `zt_registration_email_payload(p_reg)` (security definer, authenticated and service_role only) returns the recipients and the facts, and refuses unless the caller is the registrant (role `athlete`) or a meet owner/member (role `promoter`); `athlete_email` is the registrant's confirmed account email, else the form email; `promoter_email` is the meet owner's confirmed email. `received` sends the athlete mail (pending / waitlist / accepted variant) plus a promoter notice; `decision` is promoter-only and 409s unless the row is accepted or declined. Demo meets 409. `zt_mark_registration_notified(p_reg, p_kind)` stamps `registrations.email_log` (kind matches `^[a-z_]{1,40}$`); a stamped step is skipped (`already_notified`) unless `force: true`. Resend key is server-only; HTML goes through `escapeHtml` in `lib/email/layout.ts`. Verified by me on the v2 preview: one real send for the astra registration (athlete mail to astra.staging@, notice to slate.staging@), both stamped, repeat call skipped both. Questions: can a member of meet A obtain a payload for a registration on meet B (the owner/member check is per `registrations.meet_id`; confirm nothing resolves by the registrant's `user_id` alone)? With `force: true`, how many mails per minute can a registrant make the server send to the promoter, and is that worth a cap in `email_log` (count or last-sent window)? Does `decision` leak the status of someone else's registration to a registrant who guesses an id (should be 403 before any status text)? Anything in the HTML templates that takes a form field (name, emergency contact, division label) without escaping? What happens when the promoter's email is unconfirmed: the athlete mail goes and the notice is `no_address`; is the UI copy for that case right in `RegistrationsSection`?

2. **Auto-accept (032)** (`supabase/032_auto_accept.sql`, `components/promoter/ListingSection.tsx`, `components/register/RegisterClient.tsx`). `meets.auto_accept boolean not null default true` (all existing meets flipped to true; Kurt's call, no live customers). `zt_submit_registration_body` now locks the meet row `for update`, runs the existing cap/deadline/status checks under the lock, inserts the registration, and when the outcome is `pending` and the meet auto-accepts, inserts an `athletes` row (`'reg-ath-' || left(reg_id, 8)`, next lot in the division), sets the registration to accepted with `athlete_id`, touches the meet and returns `'accepted'`. The 021 wrapper (account required) is unchanged. `auto_accept` is readable through `zt_my_meets` / `zt_get_my_meet` and writable only through `zt_update_listing` (new patch key); not in the public column grant. Listing tab gained a "New Entries" select (`#listing-auto-accept`). Questions: two registrations racing on a meet one seat short of the cap: does the lock make exactly one accepted and one waitlist, and is the lot number unique per division under the race? Can the `reg-ath-` id collide with a scorer-created athlete id (scorer and builder ids come from `makeId('ath')` in `lib/meetBuilder.ts`: `ath-<ms>[-n]`; fixture promoter ids are `reg-ath-<full uuid>`; check the roster merge in `lib/sync`)? A promoter flips a meet from automatic to review while entries are pending: nothing retroactive happens, confirm the copy says so. The scorer pulls the roster from `athletes`; does an auto-accepted athlete with no bodyweight break anything in weigh-in or the board? Is "accepted" the right outcome when registration status is `waitlist`-eligible (cap reached) on an auto-accept meet: the function should still return `waitlist`, confirm.

3. **Profile links (029)** (`supabase/029_profile_links.sql`, `lib/website/profileLinks.ts`, `components/website/AccountClient.tsx`, profile page). `profiles.home_gym_id` (FK gyms, set null on delete, owner-updatable through the authenticated `update` grant; client validates uuid, server enforces the FK). `zt_profile_links(p_username)` is an anon RPC that returns `{home_gym, shows, gyms}` for PUBLIC profiles only ({} otherwise); `shows` = listed, non-demo meets owned by the profile, only when `is_promoter`; `gyms` = claimed gyms owned, only when `is_gym_owner`. The function reads `meets.owner_id` / `gyms.owner_id` inside security definer, so the badge gate is what keeps ownership private. Questions: can a private profile's ownership be inferred by calling the RPC with a username and comparing timings or error shapes? Does an unlisted or demo meet ever appear in `shows` (the where clause is `m.is_public_listed and m.is_demo = false`; confirm both columns are the ones the public pages use)? Can a user set `home_gym_id` to an unclaimed gym, and if so does the profile page link to a gym page that exists? The `/trainers` page and `mode` filter: `cleanModeParam` folds anything outside `TRAINER_MODE_OPTIONS` to ALL; any way a hyphen/underscore variant changes the query?

4. **Colour ways (030)** (`supabase/030_theme.sql`, `lib/website/theme.ts`, `components/website/ThemePicker.tsx`, `WebsiteThemeFrame brand`). `meets.theme` / `gyms.theme` jsonb, check constraints via `zt_theme_ok` (keys primary / background / secondary only, each lower-case `^#[0-9a-f]{6}$`, under 200 bytes). Client `parseTheme` re-validates and `themeCssVars` emits the values as inline `--zt-*` variables on `/gyms/<slug>`, `/shows/<slug>`, `/m/<slug>`. `gyms.theme` is written through the owner column grant (RLS owner + claimed); `meets.theme` through `zt_update_listing`. Warnings only, never refusals, for low accent contrast. Questions: is there any path for a non-hex string to reach a `style` attribute (think a row written before 030 by a service role, or a theme object with an extra key that passes the client and fails the server, or vice versa)? Does `?theme=` on the board still beat the brand theme, and does a user touching the controls drop the brand cleanly? Keyboard and screen-reader path through the picker swatches; focus ring on the preset buttons in Daylight.
