## Findings

### P-H1: HIGH, photo replacement can leave a broken saved profile photo

**`lib/auth/avatar.ts:30-39`; `lib/auth/useAuth.ts:162-169` | A successful upload removes the old object *before* `avatar_path` is updated. If the profile write fails, the database still points to the now-deleted old object; the new object is orphaned.** This can lose the user's existing photo on a transient profile-write error. An executable mocked upload confirmed the order `upload -> remove old -> profile update fails`; source inspection confirms that `setAvatar` calls `saveProfile` only after `uploadAvatar` returns. This is an ordering/data-integrity defect, **not** a reproduced Storage RLS bypass or a live induced database failure. Recommendation: upload new, save the new path, then best-effort delete old; on save failure retain old path/object and best-effort remove the orphaned new upload. `clearAvatar` already saves the empty path before attempting old-object removal. Retest both failures independently.

### P-M1: MED, database accepts nested/unrecognized PR and social structures

**`supabase/013_profile_fields.sql:23-26`; `lib/auth/profile.ts:100-123,207-217` | Checks enforce top-level array/object, count and 2 KB size, but not item/key/value shape.** A staging user-JWT PATCH with `prs:[{"lift":{"nested":"audit"},"value":["10"]}]` returned **200**. `socials:{"arbitrary":"key","instagram":{"nested":"audit"}}` also returned **200**. Four PRs, a non-array PR, an array for socials, and 10 KB values returned **400/23514** as expected. The profile is currently private to its owner; the client normalizes on read, so this is a future public-profile/data-contract risk rather than a demonstrated XSS. Add a database-side check for at most three PR objects with string `lift`/`value` and their lengths, and only named social keys with string values and lengths. Do not rely on the account form's sanitizer for direct REST clients.

### P-M2: MED, standalone public routes lack the only advertised sign-in entry

**`app/join/page.tsx:5-7`; `app/join/JoinClient.tsx:191-196`; `app/m/[slug]/ScoreboardClient.tsx:113-157` | `/join` and `/m/<slug>` do not use `WebsiteShell`, so they have no Account tab or sign-in link.** On staging the shell pages `/website`, `/how-it-works`, `/shows`, `/gyms` each had one Account link; `/join` and the demo `/m/keystone-fall-brawl-2026` had zero. `/join` offers “Back to ZeroTacky Home” as an indirect route, while the board has no equivalent. Add a compact, focusable Account/Home link on these standalone pages, without replacing the meet-day layout or crowding TV mode.

### P-L1: LOW, icon-only Configure button has no mobile accessible name

**`components/website/WebsiteThemeControls.tsx:37-40` | The text “Configure” is hidden below the `sm` breakpoint, while the button has no `aria-label` or `title`.** A 430 px staging header had an empty button name and no `aria-label`; a role-and-name locator for Configure timed out. On that same narrow header the daylight button had the correct accessible name, keyboard Enter toggled `aria-pressed`, Configure could be focused and Enter opened the Theme dialog, and Escape closed it. Account remained a focusable link. Give Configure a stable `aria-label="Configure theme"`, with its visible text unchanged on larger screens.

### P-L2: LOW, unsafe URL construction remains possible outside the sanitizer

**`lib/auth/profile.ts:85-98,207-217` | `cleanWebsite` returns an http(s) URL, but truncates the serialized URL at 200 characters without checking it afterward; `socialUrl('website', value)` returns unsanitized input unchanged.** A long URL ending in an encoded emoji was shortened to an incomplete `%` escape; direct `socialUrl('website','javascript:alert(1)')` returns that dangerous string. The normal Account path calls `cleanProfilePatch`, which dropped `javascript:` and `data:` and did not render links publicly; no XSS was observed. Store/return a complete, within-limit URL rather than cutting serialization mid-escape. Sanitize or validate at the actual href-rendering boundary when public athlete pages arrive, especially because direct REST clients can store arbitrary small social values (P-M1).
