# ZeroTacky v2 Gate 2 audit, 2026-10-17

**Verdict: merge after listed fixes. The current build is not ready to merge as is.** Two HIGH issues remain in real staging flows: a joined phone publishing a null PIN resets the server PIN to `1050`, and a successful pre-publish roster read can still be followed by publishing the old React state, silently deleting unregistered walk-ons. Accepted-registration deletion and scored-athlete deletion are now refused. Five of R1–R7 are fixed; R1 and R2 are partial.

There is also a MED workflow inconsistency in the intentionally different floor/dashboard rules. I agree that a walk-on should not block meet-day score/config publishing, but the allowed floor state must not make unrelated dashboard changes unsavable. Details and a recommended policy are below. Kurt decides the merge date; this is a code-readiness verdict.

### G2-H1 exact reproduction and why the probe can miss it

1. Stopped other scorer publishers by navigating their audit tabs away.
2. Owner read confirmed server PIN **7391**.
3. Joined phone held no local PIN, saved the authorized staging key and clicked **Publish update**.
4. Captured actual browser request: `p_meet.admin_pin:null`; response **200**.
5. Owner reread returned **1050**. A separate direct null-PIN RPC earlier in this run had produced the same result.
6. Restored this test meet's PIN to 7391 using the normal publish RPC.

`verify_008.sql:9,45-49` compares null-publish output to whichever PIN the existing probe meet already had, then sets 7391 only afterwards. If that starting PIN was 1050, the erroneous reset to 1050 would pass. I did not execute the script or establish its earlier starting PIN. That is a weakness in the probe design, not a fabricated account of its run. The mock at `test/fake_supabase.mjs:63` explicitly keeps the existing PIN, so its green test cannot validate PostgreSQL's `excluded` semantics.

### G2-H2 exact browser evidence

This was observed twice with controlled stale-phone snapshots of the same fictional meet. Initial partial-connectivity setup blocked stale GETs, then restored them before the healthy Publish click; the publish endpoint was never stubbed.

Second reproduction's actual response trace:

```text
successful roster GET: Gate2 Prepull Race, Gate2 Prepull Race Two,
                       Gate2 Reload, Gate2 Scored, Gate2 Registrant
publish RPC HTTP 200:  Gate2 Reload, Gate2 Scored, Gate2 Registrant
next roster GETs:      Gate2 Reload, Gate2 Scored, Gate2 Registrant

```

The stale phone's state temporarily included the pulled newcomers immediately after the first publish, proving the read reached React, but the captured publish request did not include them. Letting subsequent native polling and auto-republish run did not repair the server roster. The judge later lost both names. No test code manually deleted those two rows.

Earlier `prepullRecovery.hasWalkon:true` only proved local arrival and RPC success; final server/payload inspection showed it was **not** evidence of preservation. The unit fake's `onIncoming` synchronously assigns `box.state` (`controller.test.mjs:24`), unlike React, which explains why the controller-only test passes.

### Opinion on the intentionally omitted cap/division checks

I agree with keeping a floor walk-on from blocking meet-day config publishing. Adding a blanket cap guard only to `zt_publish_meet` would recreate the failure described in section 6. I do **not** agree that leaving the rest of the workflow inconsistent is finished.

My recommendation is to make capacity an intake rule: enforce it on new submissions/acceptance, allow existing floor rosters to exceed it, and let the owner close registration or save unrelated settings without first raising that intake limit. Division changes need a deliberate transfer operation that keeps the original registration as evidence and records the effective competition division. Until that exists, document and consistently enforce which actor/path may make the change. Do not claim the submitted and effective division always agree.

Live evidence: anonymous athlete upsert without a join code returned **401 / 42501**, while the valid join-code upsert moved accepted Registrant to `gate2-alt` and returned **200**; full publish accepted the move too. The registration retained its original division. An unchanged `zt_save_meet_config` then returned:

> Gate2 Registrant registered for a specific division. To move them, decline or withdraw the registration and accept it again under the new division.

Restored the athlete to the original division and removed the temporary alternate division through normal publish. Separately, a four-athlete roster with cap three was accepted by publish, but a patch only setting registration closed returned:

> The roster already has 4 athletes; the cap cannot be lower than that.

Restored the three-athlete test roster afterward. These are known-state incompatibilities, not authorization bypass claims.

## Remaining venue recommendation

Proposed server contract, not an existing validated rule: null or a JSON object containing only `facilityName`, `streetAddress`, `city`, `state`, `postalCode`, `country`; reject arrays, nested objects, non-string values and unknown keys. Suggested limits are facility 160, street 240, city 120, state 80, postal code 32 and country 80 characters, with nonblank city/state/country when a nonnull venue is publicly listed. These are recommendations for Slate/Kurt to accept, not measured requirements. Apply the same shape in the UI/API and keep text rendering escaped. Arbitrary JSON remains disclosed, not silently marked fixed.
