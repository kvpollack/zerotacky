# Astra audit of registration mail, auto-accept, profile links, and colour ways (2026-10-29)

**Fix the waitlist mail path and cap the authenticated resend path before the next release.** The mail-log authorization and owner-email disclosure also need decisions before release. I found no cross-meet payload read or HTML/CSS injection in the paths tested. This audit made no application or database changes.

## Findings

SHIP means fix before the next release. DAY-OF needs an explicit operating decision or workaround. LATER is bounded usability work. A local fake-server reproduction establishes route behavior, while staging responses establish only the named live cases.

| ID | Severity | Finding | Suggested fix |
|---|---|---|---|
| EM-01 | SHIP | **New waitlist entries get no registration mail.** The 032 body inserts a registration with `status = 'waitlist'` when the meet is in waitlist-only mode. The `received` route accepts only `pending` or `accepted` and returns 409 for `waitlist`, before either the athlete mail or promoter notice is planned. The waitlist builder exists but is unreachable for this status. A local route invocation with a waitlist payload returned 409 and made zero send attempts. | Treat `waitlist` with `waitlisted = true` as a valid received case, then send the athlete waitlist wording and promoter notice. Add an end-to-end route test for this SQL outcome, including its stamp and repeat skip. |
| EM-02 | SHIP | **A registrant can trigger repeated mail to the promoter without a send window.** `force=true` bypasses both `email_log` entries. Neither the route nor the two 031 RPCs rate-limits this operation. Three sequential calls in an isolated route mock yielded six sends, including three promoter notices. Two simultaneous `force=false` calls in the mock each read an empty log and yielded four sends before their stamps, so the stamp is not an atomic claim. This is a source and local-mock finding; no high-volume live mail was sent. | Put a server-enforced, per-registration/per-message send window and count in the database. Make send eligibility an atomic reservation before calling Resend, with a retry policy for failed sends. Restrict `force` to an authorized promoter or a separately controlled support path. Test simultaneous requests and stamp-failure retries. |
| EM-03 | SHIP | **The registrant can forge mail-log stamps.** `zt_mark_registration_notified` accepts any authenticated registrant for their own row and any 1–40 character lowercase/underscore key. There is no proof that a message was sent. Calling it with `received`, `notice`, or `decision_accepted` can suppress a later `force=false` mail, including the promoter notice or acceptance decision. The attack is established by the SQL grant and predicate, not by mutating the staging fixture. A denied cross-registrant stamp was tested. | Make stamp/reservation writes server-only and limit keys to the message states the route handles. Do not grant a browser bearer direct stamp authority. Pair the mail state with the atomic send eligibility in EM-02. |
| EM-04 | DAY-OF | **The payload RPC exposes the promoter's confirmed account email to the registrant.** A live staging call as the registrant returned `promoter_email` even though the meet's separately published `promoter_contact` is different. A browser does not need the promoter address to receive its own confirmation. This permits account-email disclosure to anyone allowed to register for that show; the presence and difference were checked without printing either address. | Separate the registrant-visible payload from the server-only recipient lookup, or have a server-owned mail operation resolve and send the notice without returning its address to the athlete bearer. Confirm whether the meet owner has expressly chosen to publish the account address. |
| EM-05 | LATER | **The promoter-notice failure is silent or misdescribed in the UI.** If the owner has no confirmed email, the route reports `notice:no_address` while the athlete message can still succeed. `describeEmailResult` checks the athlete send first and tells the athlete only about that confirmation. The promoter sees no notification that their own address prevented notices. Its generic `no_address` branch says the *athlete* has no address, even when the missing address is the promoter's. Source review only. The staging owner has a confirmed address. | Keep the athlete confirmation copy, but surface a promoter-facing notice in Listing or Registrations when the owner cannot receive mail. Match `notice:no_address` and athlete-address failures separately, and avoid promising a decision email before a send result exists. |
| AA-01 | DAY-OF | **A cap race does not produce one accepted entry and one waitlist entry in open mode.** The 032 meet-row lock serializes submissions and protects the cap and division-lot calculation. At the final open-mode seat, the first valid request can be accepted, but the next hits the full-cap exception at lines 157–159. Waitlist rows occur only after the promoter switches `registration_status` to `waitlist`, regardless of `auto_accept`. This is a source conclusion; no two-account race or fixture-cap change was performed. | Decide whether open-and-full should automatically waitlist or explicitly refuse. If automatic waitlisting is the product rule, change the branch under the existing lock and test concurrent submissions plus unique division lots. Otherwise keep the refusal and correct the acceptance criterion and customer copy. |
| CW-01 | LATER | **Preset swatches lack an explicit keyboard focus indicator.** `ThemePicker` exposes each preset as a named native button, so it is keyboard reachable and has an accessible name. Its only added ring is on `hover`, not `focus-visible`; the Daylight border can blend with the card. This is source-reviewed. No screen-reader or visual-browser verdict was reached. | Add a high-contrast `focus-visible` ring/offset to the preset and default buttons, then Tab through the picker in Daylight with a keyboard and a screen reader. |

## Coverage and limits

### 031 registration emails

- The staging `zt_registration_email_payload` returned the stamped Iron Harbor row for the owner and its own registrant. An unrelated registrant's real pending row returned 400, `You do not have access to this registration.` The preview route mapped that denial to 403. The same registrant's own `decision` request returned 403 before reporting `pending` status; an unknown UUID returned 400, `unknown registration`. These are only error-path calls, with no mail sent.
- A single `received`, `force=false` call on the already stamped row returned 200 with zero sends and `received:already_notified` plus `notice:already_notified`. The separate cross-meet membership predicate checks the row's `meet_id`, not its `user_id`; no second-meet registration was available to exercise that exact live case. Existing second-meet rows were not created for this audit.
- All form-derived HTML fields pass through `escapeHtml` in `renderEmail`, including greeting, lead, facts, subject in `<title>`, and link attributes. The subject and plain text are not HTML, so markup can remain literal there. The tests cover an athlete name with angle brackets. No live HTML-injection send was attempted.
- A direct call to `zt_mark_registration_notified` on someone else's Iron Harbor row was denied. The authorized-own-row stamp vulnerability in EM-03 is source-reviewed only. No mail stamp was added by this audit.

### 032 auto-accept

- The staging fixture read `auto_accept = true`, registration open, cap 40, and 14 roster athletes. The brief's existing pending registrations remain pending. The new toggle affects future submissions. Listing copy describes new entries but does not explicitly say it will not process existing pending rows. The SQL accepts only when its outcome is `pending`. The waitlist-only outcome stays `waitlist`.
- The meet row is locked `for update` before checking capacity, inserting, and choosing `max(lot_number) + 1` for a division. Manual acceptance also takes the meet lock before calculating its lot. This supports serialized lot assignment for these paths, but no concurrent database race was run. The `reg-ath-<8 uuid chars>` ID cannot collide by format with the builder's `ath-<millis>[-n]`; the roster merge keys by full athlete ID. A rare collision between two truncated registration UUIDs would cause an insert error rather than merge with a scorer ID.
- Missing bodyweight is permitted by the SQL and maps to an omitted optional `Athlete.bodyweight`. No consumer of that property was found in the board path reviewed. A weigh-in workflow on real scorer phones was not executed, so meet-day usability is not certified.

### 029 profile links

- The anon RPC returned `{}` for a tested unknown username. For a private profile, the SQL exits before ownership queries, also with `{}`. Timing equivalence between private and unknown names was not measured; no private-profile ownership test data was created.
- `shows` is gated by public profile plus `is_promoter` and selects `is_public_listed` and `is_demo = false`. Those are the same filters used by both public show loaders. `gyms` requires the owner badge and a claimed gym. `home_gym_id` permits an unclaimed gym; the RPC includes unclaimed/claimed only, as does `/gyms/<slug>`, so that link resolves under the current public loader.
- `/trainers?mode=in-person` and `in_person` normalize to `in_person`; unknown modes normalize to `ALL`, and the filter uses the normalized choice. The local check and existing tests cover this conversion. No hidden query branch from the spelling variation was identified.

### 030 colour ways

- Database constraints accept only lower-case six-digit hex for the known keys. All identified public render paths parse the stored theme before passing it to `themeCssVars`. A local malicious-string probe returned null; an object with an extra key kept only the validated colors. Thus no tested non-hex value reached an inline CSS variable. A database-side rejection of a malformed service-role row was not tested, and no historic malformed row was written.
- The board reads a recognized `?theme=` into `override`. `WebsiteThemeFrame` picks it ahead of the brand, and choosing a control drops the override and brand for that visit. This ordering was reviewed in source without a new browser check. Picker swatches are actual color-input and text-input controls with labels. Preset accessibility needs the focused visual check in CW-01.
